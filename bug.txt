Updated Bugs after testing of above bugs:

1. The pdf still looks concerete nothing like the invoice page even fixing for twice.

Status: Addressed again. The PDF was redesigned to mirror the app invoice page more closely, and the download now goes through the frontend route `/api/invoices/[invoiceNumber]/pdf` instead of linking directly to the backend origin. Server-side invoice calls also prefer `SERVER_API_URL` before `NEXT_PUBLIC_API_URL`.

2. Which is better notification polling or web socket. I see the order status update is working realtime. I think notification polling will cost
unnecessary charges in production.

Status: Addressed with SSE live updates. Customer notifications and customer order screens now listen to same-origin live event streams instead of polling timers. SSE is a better fit than a full WebSocket for this use case because the app only needs server-to-browser updates, automatic reconnects, and no browser-side command channel.

3. When the order is ready to pickup it shouldn't show any further status unless otp is entered. Without entering the otp i can able to complete the order.

Status: Addressed. `COMPLETED` is no longer an admin-selectable/manual status update. Orders can only move to completed through the OTP verification endpoint, while already-completed orders still display their current state in the admin UI.

4. Order not found in admin page when the status is changed to complete

Status: Addressed. The admin order detail route already uses an admin-owned lookup that can read completed orders; the frontend now preserves real fetch errors instead of showing every 401/403/proxy/backend failure as "Order not found", and admin order API proxies now prefer `SERVER_API_URL` before `NEXT_PUBLIC_API_URL`.

5. The order which had payment pending got successful later. in the order details page it shows Payment created but its status is still showing pending payment.

Status: Addressed. Pending-payment recovery now checks every live Razorpay provider order attached to the order instead of only the newest payment row, and order history/admin history also run the recovery check before rendering. Customer/admin order detail now prefer the captured payment record when multiple payment rows exist, so a later captured payment no longer displays as stale "Payment created".

6. Introduct web socket as order managmenet in admin side is not updated in realtime. and my backend is getting overloaded with notification and orders api.

Status: Addressed with admin SSE live updates. Admin order list/detail pages now subscribe to `/api/live/admin`, and the backend emits admin order update events when payment capture finalizes an order, an admin changes status, or OTP verification completes.

7. What happens when the otp is expired. It shouldn't stop order flow, as the cutomer has already paid and order is already prepared. A new otp should be generated for the same oredr 
making the older one invalid unless the order is complete.

Status: Addressed. Expired OTP verification now automatically generates a fresh pickup OTP for the same ready order, invalidating the old code and notifying the customer. Admin handover now also has a "Generate new OTP" action that force-refreshes the code even when the current OTP is still active, guarantees the visible code changes, includes order status in the notification metadata, and emits a customer/admin live order update so the customer order page refreshes and shows the new OTP.
